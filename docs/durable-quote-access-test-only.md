# Durable quote access: isolated test-only composition

Adds an opt-in composition around existing-session proof, persisted membership/version checks, per-event grants and quote operations using one PostgreSQL transaction. It does not start a server, install an authentication adapter or provision accounts, sessions, permissions, catalogs or credentials. The prepared migration is not registered with existing startup paths and permits only `test` mode.

The session adapter must be server-owned. Do not resolve an actor, tenant or permission from a request body or untrusted identity header. The database stores hashes rather than raw proof tokens. Quote data remains sealed through the existing vault. Authority rows remain share-locked until the quote transaction commits. Revocation serializes after a transaction that already holds the lock; subsequent requests are rejected. Expiry during the operation causes rollback. This does not promise cancellation of a transaction that already acquired valid authority.

Creation requires an existing, explicitly assigned event and grant. This slice does not allocate event IDs or create assignments. Status reports role-level capability only; every event operation additionally requires the event grant. FINANCE is not allowed to access this quote module. These are test policies, not configured permissions for real Gourmet staff.

Independent review found an availability issue: an indefinitely pending business callback could retain the authority locks and pooled connection. The corrective work adds a monotonic transaction deadline including acquisition, server-side statement/idle timeouts compatible with PostgreSQL 16, and permanent destruction of an interrupted lease. The pool must itself configure a finite connectionTimeoutMillis (1–30000 ms) to bound its pending acquisition queue; pipeline mode and pool onConnect/verify hooks are unsupported. The default request deadline is 5000 ms; repository-only test configuration permits 1–30000 ms. An already executing PostgreSQL statement can retain locks until the server observes disconnection or its configured statement_timeout expires; the application deadline is not a guarantee of instantaneous physical lock release. Arbitrary JavaScript callbacks are not forcibly terminated: any late continuation only retains a closed client and must not perform external side effects. Catalog adapters remain trusted, bounded providers; using the same constrained pool recursively may time out.

No COMMIT may be issued after an observed deadline. If a timeout or connection failure occurs after COMMIT was already sent, the database outcome can be uncertain: the API returns a sanitized failure and the caller must retry the existing idempotency key. Do not promise rollback for that uncertain-commit case. The ordinary expiry-before-COMMIT path rolls back quote, audit and receipt together.
